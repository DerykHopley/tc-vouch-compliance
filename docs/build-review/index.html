Sprint 3 review · how Vouch was built

Build review

Vouch was built by Claude Code agents between 2 and 12 November 2026, run by rig, a plugin that sets how agents plan, build, check and merge. This page looks at what that cost, where the tokens went, and what to change for the next project.

The short version

  • Context, not writing, is the cost. Agents wrote 26 million tokens but re-read 6 billion: each call re-reads the session's whole context. A long-lived thread gets dearer with every call.
  • A Fix cost three times as much per changed line as a Feature or a spec, and half of that was the one Fixes thread, which ran for six days with about 476,000 tokens of context on each call.
  • A Feature cost the same per line as a spec ($1.15 against $1.16 per 100 lines), without an integration branch, a ticket-writer or waiting on other specs. That's why Vouch ended building Features rather than specs.
  • Checking was cheap for what it caught: the blind verifier was 10% of the spend and the code reviews 8%. Scoring each spec with a judge cost $4 in total.

Each spec: cost and the judge's scores

A judge agent, which took no part in the build, scored each landed spec from its GitHub record and session transcripts on four rubrics (1, 0.8, 0.4 or 0.2). M7 was never scored. Cost per 100 lines rose for the polish-heavy specs (M5, M6, M9): small changes, full ceremony.

How the process changed

Each change to rig came from something seen in Vouch, and each is in rig's changelog with what would end it.

  • 4 Nov · specs with a ticket loop: each ticket built test-first by an implementer agent, reviewed, merged on green CI, then checked by a verifier that never sees the implementer's report.
  • 5 Nov · a coordinator: one thread per spec, several specs at once, and the owner's "desk": the latest message always holds everything waiting on them.
  • 6 Nov · tickets written just in time: in M2, 7 of 12 tickets written up front no longer matched the code when built. Agents decide reversible choices and flag them; only hard stops (money, secrets, live data, scope) wait for the owner.
  • 9 Nov · a judge and a retro: each landed spec scored, and the retro files proposals for rig. Three were accepted after M9: prove each claim with one test, change test setup behind one helper, a more patient merge gate.
  • 10 Nov · a wider Fixes lane: small enhancements became Fixes rather than being bundled into a spec.
  • 11 Nov · one Build level: each piece of work is chosen as a Fix, a Feature or a spec, so specs come and go without re-planning the project.

What to do differently next time

  • Restart long threads. A fresh Fixes thread every few Fixes, and the coordinator after each spec lands. GitHub holds the record, so nothing is lost, and the Fixes alone would likely have cost a third to a half less.
  • Tag every session with its unit of work from day one. Claude Code's OpenTelemetry export (here into a local Langfuse, added on 10 November) reports each call's model, effort, tokens and cost. With a tag naming the spec, Feature or Fix, this page would be a query rather than a reconstruction from transcripts.
  • Lighter models where judgement is narrow. Reviews, the verifier and the ticket-writer were 20% of the spend, all on the largest model.
  • Make Features the default and keep specs for stories that only work together.

Method. Every Claude Code transcript for this repo (sessions and their agents) was read and each model call priced at the per-token rates fitted from Claude Code's own cost telemetry. A call belongs to the spec, Feature or Fix its agent was started for, from its prompt or branch; a thread's own calls belong to what it last started, or to the spec or Feature it ran. Lines are each merged PR's additions plus deletions, tests included. The coordinator ($150) and sessions matched to no unit ($117: research and one-off jobs) are counted in the totals but not in the per-unit chart. Costs are what the same calls would cost on the API; the project ran on a subscription.
