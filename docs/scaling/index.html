Scaling Vouch

What it would take to turn Vouch from a single-company course demo into a product businesses can buy: eight areas of tech and infrastructure, each with where it stands today, what to change, and why.

Written by Claude, an agent working in Claude Code, from the code and docs only. Nothing was run and no model was called. Each point about today is marked checked (seen in the code or docs) or unverified (a reading not yet confirmed). The sizes are the writer's estimates. The open questions are research ticket #716.

In short

The biggest gap is that Vouch has no idea of a customer organisation. Every other area builds on that, so it comes first. The guards in code, the checkpointed review, the audit trail and the offline tests already hold up and carry over as they are.

The eight areas

1. Tenancy and sign-in

Size L · do first
Today
  • One current company, chosen by a developer, is shared by every user (vouch.current_company; decision 1 of 2026-11-10). checked
  • Tables are keyed by user_id or profile_id; no table has an organisation (vouch.database). checked
  • Access is Clerk sign-in plus membership of the course's Discord server (vouch.auth). checked
  • Any signed-in user can add or withdraw evidence every lead is assessed on (critique S1; per-user profiles are #163). checked
Change
An organisation id on every table, enforced by Postgres row-level security so a missed WHERE can't leak another customer's evidence. Clerk Organizations for membership, with SAML/SSO and roles: compliance lead, reviewer, read-only auditor.
Why first
It touches every table and query, so it grows more expensive with each feature added. It also closes S1 and #163 in one design. It is a data-model change, so it is the owner's call.

2. Real customer data

Size M
Today
  • Evidence goes whole to OpenRouter; redaction runs on events, logs and traces, not on what the model is sent (vouch.redaction; critique S6). checked
  • Reset demo can delete audit trail rows through a session setting (vouch.database; critique S4, kept on purpose in #629). checked
  • The app's database user likely owns its tables, so it could drop the append-only trigger. unverified
  • The schema is kept by idempotent CREATE and ALTER statements run by vouch-db-setup, with no version history. checked
  • No security headers, and Cloud Run runs as the default service account (critique S7). checked
Change
A direct model contract with EU processing and zero data retention (Anthropic, AWS Bedrock or Google Vertex). Redact before the model call. A database user that doesn't own the tables; no Reset demo in production. Versioned migrations (Alembic or similar). Security headers and a dedicated service account.
Why
A compliance buyer sends a security questionnaire before uploading anything. Vouch helps others prepare for ISO 27001, so its own handling has to pass the same reading.

3. Evidence ingestion and search

Size L
Today
  • An added document is a .md or .txt file of UTF-8 text (vouch.added_documents). checked
  • Search is a keyword match that reads the text on each call; every version of every added document is held in each process's memory (vouch.search, AddedIndex). checked
Change
Files in object storage. PDF, DOCX and XLSX parsing that keeps text exact enough for the quote check. Postgres full-text search plus pgvector, measured against today's search on the eval set. Then connectors to where evidence really lives: SharePoint, Google Drive, Confluence, Jira.
Why
Real policies and records are Office files and PDFs in those systems, and a real company's evidence won't fit in memory. Staying on Postgres avoids a second datastore. The quote check stays as it is: it checks the text, wherever it came from.

4. Runs as background jobs

Size M
Today
  • An assessment runs inside the HTTP request that streams it (vouch.runs, vouch.api). checked
  • The profile pass is one POST that can take minutes, with no progress (/api/profile-pass; critique U3). checked
  • The rate limit is held in each process's memory (RateLimit in vouch.limits). checked
  • Cloud Run is capped at one instance (--max-instances=1 --max=1 in the deploy wizard). checked
Change
A queue and workers (Cloud Tasks, Cloud Run jobs or similar). The UI reads a run's progress from the database instead of holding a stream open. The rate limit moves to Postgres or Redis.
Why
It lifts the one-instance cap and lets a lead run a whole profile overnight. LangGraph's Postgres checkpointer already makes each run resumable, so this is mostly plumbing.

5. Cost and billing

Size M
Today
  • Daily limits are per user: 30 assessments, 3 profile passes and 50 chat messages (vouch.spending). checked
  • Each run's tokens and cost are recorded in the usage table. checked
  • An assessment on Sonnet 5.5 costs about $0.10 to $0.12 (eval summary, with prompts that have since changed: critique P1). checked
Change
Budgets per organisation, metered from the usage table, then Stripe: seats, usage, or a mix. Try a cheaper model for gathering evidence and keep Sonnet for judging.
Why
A customer pays per organisation, not per user. The cheaper-gather saving is unverified until an eval run, which is paid and needs the owner's OK first.

6. Operations

Size M
Today
  • Deploys run from an interactive wizard on the owner's machine (scripts/deploy-wizard.sh). checked
  • One environment, the live one; Langfuse tracing (vouch.tracing). checked
Change
Terraform for Cloud Run, Cloud SQL, Secret Manager and the service account. A staging environment. Deploy from CI after the full lane passes. Error tracking and uptime alerts. The pipeline eval run on every prompt change, so quality numbers never describe old prompts again.
Why
A customer expects changes to be tested somewhere other than their data, and recovery not to depend on one person's laptop.

7. Catalogue

Size M
Today
  • 12 VDA ISA 2027.1 controls ship, in English and German, unchanged under CC BY-ND 4.0 (src/vouch/data/vda-isa-2027.1/). checked
Change
The full ISA catalogue, then ISO 27001 Annex A. Profiles-as-data already carry the per-company differences.
Why
Customers prepare for the whole audit, not 12 controls. ISO's own text isn't free to quote, so its licence is a question for the research ticket.

8. Code shape

Size S
Today
  • vouch.api is 2,869 lines, vouch.graph 2,161 and vouch.database 1,751, out of about 25,000. checked
Change
Split each into deeper modules along the lines tenancy and background jobs will cut anyway: routes per area, one store per table group, the graph's nodes apart from its wiring.
Why
Smaller modules let more than one developer, or agent, work at once without clashing on the same files. Doing it alongside areas 1 and 4 avoids moving the same code twice.

What to keep as it is

  • Guards in code: the exact-quote check, the wording rule, the allow-list and the call budget hold whatever the model does.
  • The checkpointed review: a run waits for the lead in Postgres and survives a restart; it is also the base for background jobs.
  • The append-only audit trail: the record an auditor wants to see, once the Reset demo exception is gone.
  • Compliance profiles as data: a new customer is a profile, not new code.
  • Offline tests on a scripted fake model: CI never pays for a model call.
